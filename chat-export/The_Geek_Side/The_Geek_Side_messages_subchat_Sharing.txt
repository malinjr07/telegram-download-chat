## Weaknesses (Known)

### Jailbreak denial-of-service
On a jailbroken device, service.isSupported may return false depending on iOS version + jailbreak combination. Some apps treat "App Attest unsupported" as "benign user on older device" rather than a spoof indicator, giving the attacker a silent degradation path. Apps should distinguish iOS-version-based non-support (benign) from jailbreak-triggered non-support (spoof).

### Server-side binding only as strong as enforcement
App Attest's cryptographic guarantees only matter if the server REQUIRES a valid assertion on every critical request. Servers that degrade to "no assertion" on failure lose the guarantee.

### SE compromise
The only theoretical path around App Attest is a Secure Enclave compromise — historically very rare, but (a) checkm8 / sep variants, (b) SEP exploits are in scope. See [[Architecture/SEP]].

### Rate-limit behavior
Apple rate-limits attestKey per-device. Attackers farming many new attestations per device hit the rate limit, which is an intentional design choice but can cause support-load on genuinely-new legitimate users (shared family iPads, etc.).

## Why This Is the Primary Counter-Bypass
Across every bypass documented in this vault, App Attest is the single primitive that most reliably survives:
- Container-swap (key is per-device, not per-container).
- DeviceCheck DNS block (different endpoint).
- In-process hooks (key outside process).
- IDFA spoofing (orthogonal surface).
- IDFV spoofing (orthogonal surface).
- Filesystem-root attacker (key in SE, not filesystem).

Many banking / crypto-wallet RASP SDKs (Appdome, Guardsquare iXGuard, Promon SHIELD) integrate App Attest attestation as a foundational signal layer.
